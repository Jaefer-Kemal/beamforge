Production systems inevitably encounter network partitions, unexpected packet bursts, OOM kills, and runtime crashes. Erlang's core design philosophy—**'Let It Crash'**—is only effective if your supervision hierarchy deterministically recovers from failures without human intervention.\n\nIn this final milestone, you subject your complete 5-module XMPP cluster to **Chaos Monkey Fault Injection**: deliberately killing key worker processes and verifying that the supervision hierarchy cleanly self-heals.\n\n> **Chaos Invariant:** When `xmpp_session_registry` is killed with `exit(RegPid, kill)`, `xmpp_sup` must immediately detect the termination, kill all downstream children (`xmpp_router`), restart the registry (creating a fresh ETS table), and restart the router.\n\n### Supervision Cascade Mechanics\nBecause `xmpp_sup` uses the `rest_for_one` strategy with child order `[xmpp_session_registry, xmpp_router]`:\n\n1. **Registry Crash**: If `xmpp_session_registry` terminates:\n   - `xmpp_router` is terminated by the supervisor (because it was started *after* the registry).\n   - `xmpp_session_registry` is started anew (`init([])` creates a new public ETS table).\n   - `xmpp_router` is restarted, binding to the fresh registry.\n2. **Router Crash**: If `xmpp_router` terminates:\n   - Only `xmpp_router` is restarted.\n   - `xmpp_session_registry` and all active client sessions remain completely undisturbed!\n\n### Step-by-Step Assignment Task\n1.
